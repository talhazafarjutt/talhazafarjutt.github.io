Replacing ingress-nginx in Production Without Breaking Anything

Jul 2026·12 min read·Talha Zafar

ingress-nginx retired in March 2026. The repository is archived and read-only — no more releases, no bug fixes, no security patches. Every CVE discovered from here on stays open forever, and it sits at the one place in your cluster that faces the public internet. When the retirement landed, roughly half of all Kubernetes environments were running this controller. So if you're reading this with ingress-nginx still at your edge, you're not alone. You're also not safe. This is the migration I ran across our clusters, in the order I ran it — not a feature comparison, not a vendor pitch, just the actual sequence of work.

Step 1 — Find out what you're actually running

Before touching anything, I built an honest inventory. You cannot plan a cutover around a controller you only half understand. Start with the controller pod itself:

kubectl get pods --all-namespaces \
  --selector app.kubernetes.io/name=ingress-nginx

Then every Ingress resource that depends on it. Some of ours declared ingressClassName, plenty of older ones still used the legacy annotation, so I matched both:

kubectl get ingress -A -o json | jq -r '.items[]
  | select(.spec.ingressClassName=="nginx"
      or (.metadata.annotations["kubernetes.io/ingress.class"]=="nginx"))
  | "\(.metadata.namespace)/\(.metadata.name)"'

Now the part that actually decides how long this project takes. The routing rules migrate in an afternoon. The annotations are the real work. Rank every nginx-specific annotation in the cluster by how often it shows up:

kubectl get ingress -A -o json | jq -r '.items[].metadata.annotations // {}
  | keys[]' | grep nginx.ingress.kubernetes.io | sort | uniq -c | sort -rn

When I ran this the first time, the output was longer than I wanted it to be. Pay special attention to anything with configuration-snippet or server-snippet. Those inject raw nginx config, they have no equivalent anywhere else, and the security hole they opened is a big part of why the project died in the first place. Every one of those is a manual rewrite and a conversation.

One last check people forget — third-party Helm charts that vendor their own ingress-nginx as a dependency:

find . -name "Chart.yaml" -exec grep -l "ingress-nginx" {} \;

If a chart installs its own copy, you either override it in values or wait for upstream to fix it. I tracked those on a separate line in the migration doc, because they're not yours to cut over and they'll quietly reinstall the thing you just removed.

Step 2 — Pick your destination before you pick your tool

There are two honest paths, and I've walked both depending on the cluster.

Path one is Gateway API. This is where all Kubernetes networking development has moved, and it's where you end up eventually regardless. The implementations worth evaluating: Cilium if it's already your CNI, because then the gateway runs on infrastructure you already operate; Envoy Gateway for the cleanest, most spec-conformant standalone option; Istio if you already run the mesh; Traefik or Kong if you want one controller that speaks both Ingress and Gateway API at once; NGINX Gateway Fabric if your team wants to stay in the nginx world.

Path two is staying on the Ingress API with a maintained controller. The Ingress API isn't going anywhere — it's frozen, not deleted. Traefik, HAProxy, Contour, and F5's NGINX Ingress Controller (nginxinc/kubernetes-ingress — a completely different codebase from the retired project, despite the maddeningly similar name) all still support it. This is the pragmatic move if you have hundreds of Ingress resources and zero capacity for a rewrite this quarter.

The rule I use: if your annotation audit came back heavy, deploy a dual-support controller like Traefik or Cilium first, swap the controller with minimal YAML changes, then convert routes to Gateway API at your own pace. If the audit came back light, or you're already on Cilium, go straight to Gateway API and skip the intermediate state. Some vendors will also sell you extended support for the retired controller if you genuinely need to buy a year — but that's a payment plan, not a plan. The rest of this write-up assumes the Gateway API path, because that's the destination either way.

Step 3 — Convert the routing

Run the official conversion tool first. It's a kubernetes-sigs project and it handles the boring 80% — hosts, paths, backends, and TLS references all become Gateways and HTTPRoutes:

ingress2gateway print --providers ingress-nginx

Treat the output as a first draft, not a finished manifest. It doesn't touch snippets and it can't make judgment calls. Everything else I translated by hand. The common annotations map like this:

  • canary + canary-weight → a single HTTPRoute rule with two backendRefs carrying weight fields (80 and 20) in plain YAML
  • ssl-redirect → an HTTPRoute on the HTTP listener with a RequestRedirect filter setting scheme https and status 301
  • rewrite-target → a URLRewrite filter with ReplacePrefixMatch — but nginx regex capture groups like /$2 have no direct equivalent, so any rewrite that leaned on captures needs rethinking, not translating
  • header manipulation snippets → RequestHeaderModifier and ResponseHeaderModifier filters

Then there's the group that doesn't live in the core spec at all: body-size limits, timeouts, rate limiting, IP allowlists, session affinity. Gateway API deliberately punted these to implementations through policy attachment. In Envoy Gateway that's BackendTrafficPolicy, ClientTrafficPolicy, and SecurityPolicy. In Cilium some of it lands in CiliumNetworkPolicy. In Traefik it's Middleware CRDs. Budget real time here — this is exactly where migrations stall, because it's per-implementation and none of it converts automatically.

Certificates keep working, which is the part people worry about most and shouldn't. cert-manager supports Gateway API natively once you flip on the gateway-api feature gate — it'll watch Gateway listeners and issue certs the same way it watched Ingress resources. external-dns similarly supports gateway-httproute as a source. Update both before cutover, not after. I made that mistake on a staging cluster once and spent twenty minutes convinced DNS was broken when it was just external-dns still watching the wrong source.

Step 4 — Run both edges in parallel

Install the new controller alongside ingress-nginx. It gets its own LoadBalancer Service and its own external IP. Nothing about the old path changes yet — this is the whole point, and it's what makes the migration safe.

Deploy the converted Gateways and HTTPRoutes pointing at the same backend Services the old Ingresses already use. Then test against the new IP directly, without touching DNS at all:

curl -H "Host: app.example.com" https://NEW_LB_IP/ -k -v

Verify parity path by path. Certificates resolve. Websocket upgrades survive. gRPC works if you serve it. And check that the backend still sees real client IPs — that usually means externalTrafficPolicy: Local on the new LoadBalancer Service plus correct forwarded-header config on the gateway, because Envoy handles X-Forwarded-For differently than nginx did. The first time through I found two services whose access logs suddenly showed the LoadBalancer's IP for every request. Caught it here, before DNS, which is the entire reason you run both edges in parallel.

Step 5 — Cut over one hostname at a time

Drop DNS TTLs to 60 seconds a full day before you start — the change has to propagate before it's useful. Then move a single low-risk hostname to the new IP and watch it for a day: error rates, latency percentiles, certificate expiry, log volume. Then the next one. There is no prize for cutting over fast.

Keep ingress-nginx running the entire time. Your rollback is a DNS record pointing back at the old IP, which with a 60-second TTL means a rollback measured in minutes, not hours. Do not delete anything while a single hostname still resolves to the old edge.

Long-lived connections deserve their own plan. Websocket sessions established against the old controller stay pinned there until they close — DNS changes don't touch a live TCP connection. So schedule the final termination of the old controller during your lowest-traffic window, and expect a reconnect storm when you do it. We moved ours to a Sunday 03:00 slot and the reconnect spike was a non-event; on a weekday afternoon it would not have been.

Step 6 — The things that bite

These are the failures I actually watched for, because none of them show up in a test curl. They show up a week later, in production, disconnected from the change that caused them.

  • Path matching semantics. nginx with use-regex: true matched paths like /api(/|$)(.*). Gateway API core guarantees only Exact and PathPrefix. RegularExpression matching exists in the spec but support is implementation-specific — check your gateway's conformance report before assuming a regex route carries over.
  • Silent monitoring loss. Every Prometheus series starting with nginx_ingress_controller_ vanishes at cutover. Any Grafana panel or alert built on those metrics goes dark without erroring. Rebuild edge alerting on the new controller's metrics before you move production traffic, or you'll be flying blind at the exact moment you most need eyes on the edge.
  • Default backend behavior. nginx served a configurable default backend for unmatched requests. Gateway implementations return their own 404s. If anything downstream depended on the old default-backend response shape, it will notice — and it won't tell you politely.
  • Body-size and timeout regressions. nginx defaulted proxy-body-size to 1m and half the clusters I've seen raised it via annotation. The new gateway ships its own defaults. File uploads that worked for years start returning 413, and nobody connects it to the migration for a week. Same story for long-running request timeouts.
The migration in numbers: both edges run in parallel from day one · rollback = one DNS record, ~60s TTL, minutes to revert · cut over one hostname at a time, watch a day each · zero dropped requests across the fleet · old controller scaled to zero only after 1–2 weeks of soak per host

Step 7 — Decommission properly

After every hostname has lived on the new edge for one to two weeks of soak, scale the ingress-nginx deployment to zero and leave it there for another week. If nothing screams, delete the Helm release, delete the old Ingress manifests from Git so nobody reapplies them by accident, and remove the old LoadBalancer Service so you stop paying for the IP. That last one is easy to forget and shows up on the cloud bill instead of in the cluster.

Then — since you're now on Gateway API — split ownership the way the spec intends. Infrastructure owns the GatewayClass. The platform team owns the Gateway. Application teams own their own HTTPRoutes in their own namespaces, and any cross-namespace reference requires an explicit ReferenceGrant. That separation is the actual payoff of this whole thing. The retirement forced my hand, but the architecture I landed on is genuinely better than the one I left. That doesn't happen often with a forced migration, so I'll take it.

What I'd tell myself before starting

  • The routing is an afternoon. The annotations are the project. Audit them first and let that number set the timeline.
  • configuration-snippet and server-snippet are pure manual work — no tool converts raw nginx config, so surface them on day one.
  • Run both edges in parallel and test against the new IP with a Host header before DNS ever changes.
  • Rebuild your edge dashboards and alerts on the new metrics before cutover — the old nginx_ingress_controller_ series die silently.
  • Cut over one hostname at a time with a 60-second TTL. Slow is the feature, not the bug.
